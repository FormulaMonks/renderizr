## Findings: what Structurizr does when a reader selects a perspective

Upstream: `structurizr/structurizr` at commit `e3a736a90194d3ac692ad7b5c1c7a48287355347` (shallow clone, read as data). Paths below are relative to `structurizr-application/src/main/` unless they say otherwise; `diagram.js` stands for `resources/static/static/js/structurizr-diagram.js`.

### Summary

A perspective in Structurizr is a highlight mode. The reader picks one name from a modal list of every perspective name in the workspace (binoculars button or the `p` key); the choice lives in the diagram's filter state, so it stays on through every change of view until the reader picks "(none)". With a perspective on, every element and relationship that carries the perspective keeps full opacity and takes the `Perspective:<name>` style (or a `Perspective:<name>[value==X]` style that matches its value, which wins over the plain one), while every element and relationship without it fades to opacity 0.1. Whenever anything fades, every element boundary fades to 0.1 too, regardless of whether its element carries the perspective; groups and the enterprise boundary keep full opacity. Nothing on the diagram itself changes text: an element keeps its name, description and metadata, and a relationship keeps its label text, which only takes the perspective color. The perspective's description, URL and value appear only in the hover tooltip, which the perspective turns on and which then shows the perspective section in place of tags, properties and URL. A `?perspective=` query parameter selects one at load, but picking one in the modal never writes it back to the address. PNG and SVG exports serialize the live diagram, so they draw the faded and restyled state; thumbnails are skipped while a perspective is on. Renderizr already ports the style matching in `src/model/styles.ts`, but nothing in the engine passes a perspective, so a reader can select nothing and nothing fades today.

### How a reader picks a perspective

- The control is a pair of buttons with binoculars icons, `#perspectivesOnButton` and `#perspectivesOffButton`, in the diagram controls; both open the same modal (verified, `webapp/WEB-INF/fragments/diagrams/controls.jspf` lines 17 to 18 and 38 to 39). The "on" button shows only when the workspace has at least one perspective name (verified, `webapp/WEB-INF/fragments/diagrams/perspectives.jspf`:`initPerspectives`). While a perspective is on, the filled binoculars button shows with the title `Perspective: <name>` (verified, `perspectives.jspf`:`openPerspectivesModal`).
- The `p` key opens the same modal, in the server app and in the static export (verified, `webapp/WEB-INF/jsp/diagrams.jsp` around line 920; `resources/static/static/static.html` around line 303, and its help text lists "Perspective (`p`)" at line 45). The cookbook names the binoculars button and the `p` key too (verified, https://docs.structurizr.com/dsl/cookbook/perspectives-static/).
- The modal is the generic navigation modal with a "(none)" entry first, then the perspective names (verified, `perspectives.jspf`:`openPerspectivesModal`, `static.html`:`openPerspectivesModal`).
- The list holds every distinct perspective name on any element or relationship in the whole workspace, trimmed, deduplicated and sorted alphabetically; it does not depend on the current view (verified, `resources/static/static/js/structurizr-workspace.js`:`getPerspectiveNames`). So a name can appear that no element in the current view carries.
- Picking "(none)" clears the perspective (verified, `perspectives.jspf`:`deactivatePerspective`, `diagram.js`:`clearPerspective`).
- The choice survives a change of view. The perspective lives in the module-level `filter` object (verified, `diagram.js` lines 89 to 94), and `renderView` ends with `filter.id++; runFilter(filter.id);`, which reapplies it to the new view (verified, `diagram.js`:`renderView` around line 977). Nothing in `renderView` resets `filter.perspective` (verified by reading the function's reset block around line 386, which clears `enterpriseBoundary` and group maps but not the filter).
- The address carries the perspective only one way. A `?perspective=<name>` query parameter selects it at load through `setPerspective` (verified, `diagrams.jsp` lines 353 to 361; `static.html` lines 243 to 247), and embeds forward it (verified, `resources/static/static/js/structurizr-content.js` line 110; `webapp/WEB-INF/jsp/playground.jsp` lines 192 to 194). Picking one in the modal calls `showPerspective`, which touches no URL (verified, `diagram.js`:`showPerspective`, `perspectives.jspf`). Only "open the current diagram in a new window" appends `?perspective=` to the new URL (verified, `diagrams.jsp`:`openCurrentDiagramInNewWindow`). Views switch through the hash, so a query parameter present at load stays in the address across views (inferred from hash navigation, `diagrams.jsp` thumbnail click handler sets `window.location.hash`).
- No view property or DSL setting selects a default perspective. The only perspective view or viewset properties are `structurizr.perspective.interval` (default 60000 ms) and `structurizr.perspective.timeout` (default 10000 ms), both for dynamic perspectives (verified, `diagram.js`:`runFilter`, `runDynamicPerspective`; a repo-wide grep for `structurizr.perspective` finds nothing else; the Java side under `structurizr-core` holds the `Perspective` model, name, description, value and url, and no view setting).

### Fading

- `runFilter` uses `const hiddenOpacity = '0.1'` (verified, `diagram.js`:`runFilter`).
- An element in the view without the selected perspective gets `hideElement(element.id, '0.1')`, which sets CSS opacity on the element's `.structurizrElement` group: shape, name, description, metadata, navigation icons and icon all fade together (verified, `diagram.js`:`hideElement` and the shape `markup` strings around line 7198).
- An element with the perspective gets `showElement`, opacity 1.0 (verified, `diagram.js`:`runFilter`, `showElement`).
- A relationship without the perspective gets `hideRelationship(id, '0.1')`, opacity on the whole link view, so line, arrowhead and label fade together (verified, `diagram.js`:`hideRelationship`). This covers every drawn copy of the relationship, including dynamic-view `id/order` copies (verified, the `id.split('/')[0]` match).
- A relationship counts as carrying the perspective when it or, recursively, its linked relationship (`linkedRelationshipId`, for implied relationships) carries it (verified, `diagram.js`:`getPerspectiveForRelationship`; changelog entry for upstream issue 130, `changelog-application.md` line 32).
- The perspective combines with the tag filter: an item that fails the tag filter fades to 0.1 before the perspective is checked, and an item passing both gets the perspective treatment (verified, `diagram.js`:`elementMatchesFilter`, `relationshipMatchesFilter`, `runFilter`).
- Hover tooltips do not open on faded items (verified, `diagram.js`:`showTooltipForElement`, `showTooltipForRelationship` return early when the item lacks the perspective).

### What an element shows

- The diagram text does not change. `runFilter` only calls `changeColourOfCell` (fill, stroke, text color) and opacity helpers; no code path replaces the name, description or metadata text with perspective content (verified, `diagram.js`:`runFilter`, `applyElementStyleForPerspective`, `changeColourOfCell`; a grep of `diagram.js` for "perspective" finds no text change).
- The perspective's details appear only in the tooltip. Selecting a perspective turns tooltips on (`tooltip.disable(); toggleTooltip();` leaves them enabled) and clearing it turns them off again (verified, `perspectives.jspf`:`openPerspectivesModal`, `deactivatePerspective`; `diagrams.jsp`:`toggleTooltip`). The `?perspective=` load path does the same (verified, `diagrams.jsp` lines 359 to 360).
- In perspective mode the tooltip drops tags, properties and URL and shows a "Perspective: <name>" section with the description, the perspective URL (dynamic perspectives) and "Value: <value>" when set (verified, `resources/static/static/js/structurizr-tooltip.js`:`showTooltipForElement`, `showTooltipForRelationship`, `renderPerspective`). The tooltip uses the perspective style's colors (verified, `diagram.js`:`showTooltipForElement` passes `_perspectiveStyle`). The diagram page passes `header = false`, so the element's own name, metadata and description do not appear in the tooltip either (verified, `diagram.js` calls with `false`).

### Boundaries, groups, deployment nodes and instances

- Element boundaries (software system and container boundaries in `boundariesByElementId`) never take a perspective style and never check the perspective. If any item faded, every one of them fades to 0.1; if nothing faded, they stay at 1.0 (verified, `diagram.js`:`runFilter` end, `hideBoundaries`, `showBoundaries`, `addElementToBoundary`).
- Groups live in `groupsByName`, not in `boundariesByElementId`, so they keep full opacity and their style (verified, `diagram.js`:`registerGroup`, `hideBoundaries`). The enterprise boundary lives in its own `enterpriseBoundary` variable and also keeps full opacity (verified, `diagram.js` line 57 and around line 688).
- Deployment nodes are cells in `cellsByElementId`, so they behave like elements: a deployment node without the perspective fades to 0.1 and one with it takes the style through the `structurizr.deploymentNode` branch of `changeColourOfCell` (verified, `diagram.js` line 768, `changeColourOfCell`). Because JointJS draws embedded cells as siblings, a faded deployment node fades only its own box and label, not the instances nested in it (inferred from JointJS rendering; the fade targets `#<view id> .structurizrElement`, which holds the node's own markup only, verified in the deployment node `markup` around line 7283). The DSL allows `perspectives` on deployment nodes and infrastructure nodes (verified, https://docs.structurizr.com/dsl/language).
- Software system and container instances fall back to the perspectives of what they instantiate when they carry none of their own under that name (verified, `diagram.js`:`getPerspectiveForElement`; tooltip mirrors it in `structurizr-tooltip.js`:`showTooltipForElement`).

### Relationship labels

- The label text stays the same. The perspective color applies to the line stroke and to the fill of label 0, and of label 1 when the link has three labels (verified, `diagram.js`:`changeColourOfLine`). Only `color` is read from a relationship perspective style; thickness, dash, routing and the rest stay as computed (verified, `diagram.js`:`applyRelationshipStyleForPerspective`).
- A faded relationship fades its label with it, because the opacity sits on the whole link view (verified, `diagram.js`:`hideRelationship`).

### How `[value==X]` styles combine with `Perspective:<name>`

- Candidates are element (or relationship) styles from the themes, then the workspace, whose tag starts with `Perspective:<name>` and whose `colorScheme` is unset or matches the current one (verified, `resources/static/static/js/structurizr-ui.js`:`getElementStylesForPerspective`, `getRelationshipStylesForPerspective`). The match is a prefix test, so `Perspective:Ownership` also collects `Perspective:OwnershipTeam` styles (verified, `tag.indexOf(tag) === 0`).
- `findStyleForPerspective` takes the last candidate without `[` as the base, then lets the last `[value==X]` candidate whose X equals the perspective's value replace it (verified, `diagram.js`:`findStyleForPerspective`). The two do not merge: a value style without `background` falls back to the element's computed background, not to the plain perspective style's background (verified, `applyElementStyleForPerspective`).
- Elements take `background`, `color` and `stroke`; an unset background or color keeps the computed one, and an unset stroke becomes the chosen background shaded 10% (darker in light mode, lighter in dark mode) (verified, `diagram.js`:`applyElementStyleForPerspective`, `darkenPercentage = -10`, `structurizr-util.js`:`shadeColor`). Shape, size, border, opacity and icon do not change.
- When no style matches, the item keeps its computed colors but still stays at full opacity (verified, the `else` branches of `applyElementStyleForPerspective` and `applyRelationshipStyleForPerspective`).
- The cookbook shows the plain style adding a stroke and value styles coloring High, Medium and Low (verified, https://docs.structurizr.com/dsl/cookbook/perspectives-static/).
- Dynamic perspectives (`url`) count as present; upstream fetches the URL, stores the body (or the HTTP status when the body is empty or the call fails) as the value, applies the style when the call returns and polls again on the interval (verified, `diagram.js`:`runFilter`, `runDynamicPerspective`; https://docs.structurizr.com/dsl/cookbook/perspectives-dynamic/).

### A view with none of the perspective's elements

- Every element and relationship fades to 0.1, and since items faded, every element boundary fades too; groups and the enterprise boundary stay at full opacity (verified, `diagram.js`:`runFilter`, `hideBoundaries`). No message, toast or empty state appears (verified by absence: no such code in `runFilter`, `perspectives.jspf` or `static.html`). The perspective stays selected for the next view (verified, see the pick section).

### Exports

- PNG and SVG exports draw the selected perspective. `exportCurrentDiagramToSVG` serializes the live canvas (`getSvgOfCurrentDiagram` returns `canvas.html()`), and `exportCurrentDiagramToPNG` rasterizes that SVG (verified, `diagram.js`:`getSvgOfCurrentDiagram`, `exportCurrentDiagramToSVG`, `convertDiagramToPNG`). The opacity and color changes are inline `style` attributes set by jQuery `.css`, and the export only strips `class`, `data-type` and `model-id` attributes, so they survive (verified for the regexes; inferred that jQuery writes inline styles into the serialized markup).
- The diagram key does not reflect the perspective (verified by absence: no perspective reference in `exportCurrentDiagramKeyToSVG` or the key code).
- Thumbnails are not regenerated while a perspective (or a tag filter) is on (verified, `diagrams.jsp`:`refreshThumbnail`).

### What Renderizr does today

- `src/model/styles.ts` ports the style half: `perspectiveStyle` matches upstream `findStyleForPerspective` (prefix test, last plain style, then a matching `[value==X]` replaces it), with candidates filtered by scheme through `inScheme`; `findPerspective` ports `getPerspectiveForElement` with the instance fallback; `findElementStyle` and `findRelationshipStyle` take an optional `perspective` and fold the override into the resolved style; `findBoundaryStyle` passes it through.
- The engine never passes a perspective. `src/engine/react-flow/graph.ts` calls `findElementStyle(model, placed.element, colorScheme)` (line 853), `findRelationshipStyle(model, …, colorScheme)` (line 1015) and `findBoundaryStyle(model, boundary.element, scheme)` (line 670) without one, and `src/engine/contract.ts` has no perspective in its options or handle. So today a reader cannot select a perspective, nothing fades, and no tooltip exists to show a perspective's description or value. `GLOSSARY.md` and the ADRs do not name perspectives. `test/model.test.js` covers the style matching (`describe("perspectives")`, line 367).
- Differences from upstream in the ported matching:
  - Linked relationships: upstream `getPerspectiveForRelationship` follows `linkedRelationshipId` recursively; Renderizr `findPerspective` only falls back for items with a `type`, which relationships lack, so an implied relationship never finds its source's perspective (upstream issue 130 again).
  - Dynamic perspectives: upstream treats an item with a `url` perspective as carrying it (full opacity, style once the value arrives); Renderizr `findPerspective` returns `undefined` for them, which under a future fade would fade those items instead of highlighting them.
  - Stroke shading: upstream lightens 10% in dark mode; Renderizr darkens 10% in both schemes (documented in the file header as a deliberate change).
  - Boundaries: upstream never styles a boundary by perspective and fades all boundaries when anything fades; Renderizr `findBoundaryStyle` runs `findElementStyle` with the perspective, so a boundary element that carries the perspective would take the perspective stroke and color (its background is overridden by the `Boundary` styles). Deployment nodes return that style unchanged, which matches upstream's coloring of deployment node cells.
  - Relationship color: upstream falls back to the computed color when the matched style lacks `color`; Renderizr only overrides when `override.color` is set, which has the same result.
  - Fading, the selected-perspective state and the tooltip are not ported at all.

### Left over

- Picker: where does the control live in Renderizr's page (toolbar button, menu, keyboard `p`), and does its list hold every perspective name in the workspace as upstream does, or only the names the current view carries?
- Address: does Renderizr write the selected perspective into the address (the hash or a query parameter) so a link reopens it, or copy upstream and only read `?perspective=` at load?
- Persistence: does the selection stay on across views as upstream does, and across the workspace trail when a set renders several workspaces?
- Fade: do we copy upstream's opacity 0.1 and its rule that all element boundaries fade when anything fades, or fade a boundary only when none of its children carries the perspective?
- Groups and the enterprise boundary: do they keep full opacity as upstream does?
- Perspective content: upstream shows the description and value only in a tooltip Renderizr does not have; do we add a tooltip, show the value on the element in place of its description or metadata, or show nothing beyond color?
- Label layout: if the value or description goes on the diagram, which label does it replace and does the layout reserve room for it?
- Empty view: does a view with none of the perspective's items fade silently as upstream does, or tell the reader?
- Exports: does a PNG or SVG export draw the selected perspective (upstream does), and does the export file name or diagram metadata say which perspective it shows?
- Dynamic perspectives: do we keep ignoring `url` perspectives, and if so do their items fade, highlight without a value style, or leave the picker?
- Port fixes: do we fix the linked-relationship fallback in `findPerspective` now, and do we keep the dark-mode stroke deviation for perspective styles?
- Mermaid: do Mermaid diagrams take part in perspectives at all, given their nodes carry no perspectives?
- Edit mode: is the perspective picker available in edit mode, and does a faded item stay selectable and draggable there?
