# What order and animation a Mermaid flowchart source carries

A Mermaid flowchart's source carries one order: the order its edges appear in. Mermaid numbers edges that way, `linkStyle` counts them that way and Renderizr's model keeps it. Nothing in the grammar says "this edge comes after that one" as an author's intent, so a step order read from a flowchart is a reading of declaration order. Mermaid's own edge animation (`e1@{ animate: true }`, `e1@{ animation: fast | slow }`, and a `classDef` with a CSS `animation`) is a continuous dash that runs along an edge forever. It has no order and no step. Renderizr's pinned parser keeps `animate` and `animation` on every edge, and Renderizr drops them with no warning today.

Every finding below says whether it is **verified** (run or read in the code at the pinned tag) or **inferred**.

## Sources

- Renderizr's parser: `scripts/mermaid/parser.js`, generated by `pnpm mermaid:parser` from `mermaid@12.2.0` (`MERMAID_VERSION` in `scripts/mermaid/generate/index.js`).
- Mermaid's source at the tag `mermaid@12.2.0`, the checkout the generator keeps in its cache folder: `packages/mermaid/src/diagrams/flowchart/flowDb.ts`, `packages/mermaid/src/rendering-util/rendering-elements/edges.js`, `packages/mermaid/src/styles.ts`, `packages/mermaid/src/docs/syntax/flowchart.md` and `packages/mermaid/CHANGELOG.md`.
- [probe.js](237/probe.js) runs the parser and `readFlowchart` on small sources in plain Node; [probe-output.txt](237/probe-output.txt) holds what it printed. Run it from the repo root with `node research/237/probe.js`.

## The order a flowchart carries

- **Declaration order (verified).** FlowDB pushes every edge onto `edges` as the parser meets it, and `getData()` returns them in that order. A chain (`A --> B --> C`) and a fan (`A --> B & C --> D`) expand left to right: the fan gives A→B, A→C, B→D, C→D. Nodes keep the order they first appear in, even when an edge names them.
- **`linkStyle` indexes (verified).** `linkStyle 1` styles the second edge declared, whatever its place in the drawing. The index is a position in declaration order and says nothing of its own about order: in the probe, `C --> D`, `A --> B`, `B --> C` with `linkStyle 1` styles A→B.
- **Edge ids (verified).** `A e1@--> B` gives the edge the id `e1` and `isUserDefinedId: true`. An edge without one gets `L_<start>_<end>_<n>`. An id is a name: `e2` before `e1` is legal, and Mermaid reads no number from it. A repeated id goes to the first edge only; the second falls back to `L_B_C_0`. On a chain with one id (`A e1@--> B & C`), the id goes to one expanded edge only.
- **The author's intent (inferred).** Nothing else in the grammar orders edges: no step, order or sequence field, and `@{ … }` metadata on an edge reads only `animate`, `animation` and `curve` (every other key, such as `speed`, is dropped). A dynamic view's `order` has no counterpart. An author who wants a flowchart read in an order writes the edges in that order, and nothing tells that apart from an author who wrote them in any other order.
- **What Renderizr keeps (verified).** `readFlowchart` numbers edges `"0"`, `"1"`, … in declaration order, as `linkStyle` counts them, and drops the author's edge ids. Declaration order survives into the page's model; an `e1` doesn't.

## Mermaid's own edge animation

- **When it arrived (verified).** Mermaid 11.5.0 added edge ids and their animation ("Adding support for animation of flowchart edges", with a follow-up fix for edge ids, both in the 11.5.0 changelog). 11.10.0 added a per-edge `curve` through the same metadata; 11.13.0 added animation under the hand-drawn look. The use case diagram reads the same `animate` and `animation` keys.
- **The syntax (verified).** Give the edge an id, then set its metadata on a line of its own: `e1@{ animate: true }` or `e1@{ animation: fast }` (or `slow`). Mermaid's docs call `animation: fast` the same as `animate: true, animation: fast`. The metadata must follow the edge: written before it, `e1@{ … }` makes a node named `e1` instead, and Renderizr draws that node.
- **What Mermaid draws (verified, from `edges.js` and `styles.ts`).** `animate: true` adds the class `edge-animation-fast` to the edge's `<path>`; `animation: <name>` adds `edge-animation-<name>` and wins over `animate`. The diagram's CSS holds:

  ```css
  @keyframes dash { to { stroke-dashoffset: 0; } }
  .edge-animation-slow { stroke-dasharray: 9,5 !important; stroke-dashoffset: 900; animation: dash 50s linear infinite; stroke-linecap: round; }
  .edge-animation-fast { stroke-dasharray: 9,5 !important; stroke-dashoffset: 900; animation: dash 20s linear infinite; stroke-linecap: round; }
  ```

  So an animated edge draws dashed, and its dashes crawl from source to target without end, 900 units every 20 or 50 seconds. Every animated edge runs at once. Any other name (`animation: medium`) adds a class with no CSS, so the edge draws plain.
- **`classDef` animation (verified).** `classDef animate stroke-dasharray: 9\,5,stroke-dashoffset: 900,animation: dash 25s linear infinite;` with `class e1 animate` puts those declarations in the edge's inline style, and the `dash` keyframes from Mermaid's CSS run them. Mermaid also counts an edge animated when its class styles hold `animation`, and then skips the neo look's own dash array. A `linkStyle` with `animation: …` works the same way in Mermaid (inferred: the style reaches the path's inline style the same way).

## What Renderizr does with it today

All verified with the probe against `mermaid@12.2.0`'s parser and `readFlowchart`:

| Source | FlowDB and `getData()` | Renderizr's model | Ignored-styling warning |
| --- | --- | --- | --- |
| `e1@{ animate: true }` | `animate: true` on edge `e1` | dropped | none |
| `e1@{ animation: slow }` | `animation: "slow"` | dropped | none |
| `e1@{ curve: stepBefore }` | `interpolate` / `curve` | dropped | none |
| `e1@{ animation: medium }` | `animation: "medium"` | dropped | none |
| `classDef animate …` + `class e1 animate` | class on the edge, its styles in `cssCompiledStyles` | the edge's class dropped | `stroke-dashoffset, animation` (from checking the `classDef` itself) |
| `linkStyle 0 …, animation: dash 5s …` | `style` on the edge | `styles` kept | `animation` |
| edge id `e1` | `id: "e1"`, `isUserDefinedId: true` | id becomes the index | none |

So `animate` and `animation` vanish silently, while the CSS route warns. An edge's class never reaches the page's model at all, whatever it holds. A side finding: Mermaid's `linkStyle` doesn't unescape `\,` the way `classDef` does, so `stroke-dasharray: 9\,5` in a `linkStyle` splits into `stroke-dasharray: 9\` and `5`, and the warning lists `5`.

The page plays no animation for a Mermaid diagram: `animationOf` gives one to a dynamic view with ordered relationships or a static view with two or more `animations` entries, and an image view is neither, so the animation group hides (verified by reading `src/model/animation.ts`).

## Does anything step through a flowchart

- **Mermaid (verified at 12.2.0).** No Mermaid type steps. The only animation in Mermaid's syntax docs is this edge animation, in flowcharts, use case diagrams and agent flows, and its source holds no step or player code.
- **draw.io (from its docs, not tried).** draw.io offers both kinds: continuous "flow animation" styles on connectors, and page animations, an ordered list of actions (show a cell, wait, play together) that plays in lightbox or presentation mode. The order there is a list the author writes beside the diagram, much like a static view's `animations` list.
- **Others (searched, nothing found).** A web search found no tool that steps through a Mermaid flowchart. People who want it render the SVG and reveal it with their own script.

## What it means for a flowchart's animation

- A flowchart can step only in declaration order, or in an order written somewhere other than the Mermaid source. Declaration order is real and kept, but authors write edges in whatever order reads well in text, so a step order from it is a guess at intent.
- Mermaid's edge animation is a different thing from **Animation** in the glossary: continuous, per edge, with no step. It needs a word of its own if Renderizr draws it, and an entry in the ignored-styling warning if it doesn't.
- Drawing it would cost little: the parser already hands over `animate` and `animation`, and the effect is a dash array and a CSS keyframe on an edge's path.
