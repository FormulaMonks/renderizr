## Answer

The documentation and decisions pages render GitHub's tables, collapsed sections, fenced code, alerts, `~~strikethrough~~`, `<kbd>`, `<sub>` and `<sup>` today, and leave the rest as the text the author typed: footnotes, task list items, emoji shortcodes, math, diagrams and bare URLs. Collapsed sections and `<kbd>` render without GitHub's styling, highlighting covers only 11 languages, and images that follow the color scheme show both images or follow the system instead of the page theme. References such as `#26`, commit SHAs, mentions, permalink snippets and keywords stay plain text, which matches how GitHub renders a Markdown file in a repository: GitHub links them only in issues, pull requests and comments. The AsciiDoc pass covers headings, lists, tables, source blocks and plain admonitions, and turns collapsible blocks and example blocks into code blocks. A decision renders every feature the way a section does, without the page split. Cheap fixes cover most of the gap: `linkify` is free because markdown-it already ships linkify-it, footnotes and task lists each add about 1 to 2 percent of the documentation runtime, and `<kbd>`, `<details>` and the color scheme images need CSS and a few lines of code. Math roughly doubles the documentation runtime, unless the build renders it, and Mermaid, GeoJSON, TopoJSON and STL have no fit that stays offline at a sane weight. Separately, `--single-file` drops every blank line from the documentation, which breaks paragraphs, collapsed sections and code blocks in every single-file build (see _Surprises_).

The fixture is `test/__fixtures__/github-formatting.json` on the branch `chore/328/github-formatting-audit`: one section per feature, written the way GitHub's docs write it, an AsciiDoc section with the counterparts that exist, a section that splits into pages, a fenced `structurizr` block of a realistic workspace and a decision that uses a few of the features. Render it with `pnpm render test/__fixtures__/github-formatting.json`, with and without `--single-file`.

## Split behavior

The documentation page opens a page at every heading of the shallowest level below the section title, so most sections of the fixture split. `17-split-pages` shows the cases.

- **Footnotes.** With no footnote support, each definition renders where the author wrote it, as part of a paragraph. markdown-it-footnote, like GitHub, moves every definition to the end of the section, so the definitions land on the last page while their references sit on earlier ones. The page turns a click on an in-content link into a page change only when the target is a top-level heading, so a reference to a definition on a hidden page does nothing. We checked this with a reference added to the rendered page by script, since no footnote plugin is wired in; by the same code, a back reference to an earlier page does nothing either. A fix either places each definition on the page of its first reference, or maps footnote ids to pages the way heading ids map today.
- **A heading inside `<details>`.** The heading stays inside the `<details>`, and the `<details>` stays whole on its page. The heading never opens a page, never joins the documentation menu and never gets an address of its own: `?subsection=a-page-level-heading-inside-details` lands on the section's intro and drops the subsection from the address, and a link to it from another page does nothing. It also keeps the level markdown-it-shift-headings gives it (a `##` becomes `h3`), while the page's own headings are renumbered from `h1`, so it reads one level lower than a `###` subheading outside the `<details>` on the same page.
- **A `<details>` without blank lines.** `<details><summary>…</summary>` followed by Markdown on the next line stays raw text up to `</details>`, on GitHub as here, since CommonMark reads it as one HTML block.

## Surprises

- **`--single-file` drops every blank line from the documentation.** The single-file plugin ends with `html.replace(/\n\s*\n/g, "\n")` over the whole page (`scripts/plugins.js`), and esbuild writes the workspace's section and decision content as template literals with real line breaks. Paragraphs then merge into one, a `<details>` written the way GitHub's docs write it swallows the rest of its section as raw text (so the rest of the section also drops out of the menu), footnote definitions merge into the paragraph above, and code blocks lose their blank lines. The single file of Renderizr's own architecture site embeds its documentation without blank lines the same way. The multi-file build renders the fixture correctly; `--artifact` carries the workspace in its own JSON file, which keeps its blank lines (not driven in a browser). This one deserves its own bug, whatever the map decides.
- **`linkify` costs nothing.** markdown-it 15 imports linkify-it unconditionally, so the documentation runtime already carries it.
- **The image resolver sees only Markdown images.** Raw HTML (`<img>`, `<picture>`, `srcset`) and any image path with a fragment keep their relative paths, which point nowhere in a single file. markdown-it also refuses `data:image/svg+xml` in a Markdown image (it allows only GIF, PNG, JPEG and WebP data URIs), so an inline SVG stays text.
- **The AsciiDoc pass reads more than it means to.** Its attribute substitution rewrites TeX braces, and any `====` example block becomes a code block, which is why collapsible blocks and admonition blocks read as code.
- **The decisions page never converts AsciiDoc.** Only the documentation page calls the AsciiDoc pass, so a decision written in AsciiDoc goes to markdown-it as it is. The fixture holds no AsciiDoc decision; this comes from reading `src/pages/adrs.ts`.
- **Two quiet differences from GitHub across all content.** The typographer turns quotes into curly quotes and `--` into dashes, which GitHub leaves alone, and raw HTML keeps every tag and attribute (a `style` stays), where GitHub sanitizes it.

## How we measured

- The documentation runtime is `renderizr-docs.js` from `pnpm render test/__fixtures__/github-formatting.json --artifact` at 3.1.0. Every percentage divides by its minified size, or by its gzipped size for the gzipped figure.
- esbuild 0.28.2 bundled a baseline entry with the markdown stack the documentation runtime ships (markdown-it 15.0.3, markdown-it-shift-headings, markdown-it-anchor and highlight.js core with the 11 languages), minified, and then the same entry with one candidate added and in use. The cost is the difference, raw and gzipped at level 9. The baseline alone is about 80% of the documentation runtime. texmath was measured without the KaTeX copy it requires as a fallback, which an integration would alias away.
- npm metadata (version, last publish, license, weekly downloads) comes from the registry and the npm downloads API on 2026-11-13.
- GitHub's side comes from its advanced formatting docs and from GitHub's Markdown API: in `markdown` mode the API renders like a repository file (references stay text, bare URLs link), and in `gfm` mode with a repository context it renders like a comment (references link). The API renders neither math, Mermaid nor alerts, so those rows follow GitHub's docs.
- We drove the multi-file build over HTTP and the single file over `file://` in headless Chrome, in the light and dark color schemes, and with the page theme set apart from the system's.

Not checked: GitHub's rendering of AsciiDoc (the API has no AsciiDoc mode, so the AsciiDoc column compares with Asciidoctor's documented output); how GitHub treats a lowercase alert marker such as `[!tip]` (an alert here) and text after the marker (a plain blockquote here); whether github.com draws task list checkboxes in a repository file, since the API's `markdown` mode leaves them as text and its `gfm` mode draws them; the `--artifact` folder in a browser (only measured); and a footnote plugin wired into the page.
