# Compound automatic layout: Dagre or ELK for nested boundaries

Resolves [#25](https://github.com/FormulaMonks/renderizr/issues/25), a research ticket under the React Flow engine effort ([#21](https://github.com/FormulaMonks/renderizr/issues/21)). React Flow does no layout of its own, so every view that carries `automaticLayout` instead of stored coordinates needs a layout library that understands nesting: a software-system boundary around containers, groups inside boundaries, deployment nodes several levels deep. This page compares `@dagrejs/dagre` 1.1.8 (already a dependency, and what the vendored Structurizr renderer uses through `@joint/layout-directed-graph`) with `elkjs` 0.12.0 (`elk.layered`, `hierarchyHandling: INCLUDE_CHILDREN`), measured on the Big Bank plc example workspace, and ends with a recommendation.

**Recommendation in one line:** keep Dagre as the layout engine, feed it the compound graph the way the current renderer does, and add two small guards (anchor nodes for edges that start or end at a boundary, and JointJS's fit-to-children resize pass) rather than take on ELK's 430 kB gzipped engine for a layout that is tidier but visibly different from what Structurizr users see today.

## What the current renderer does

`vendor/structurizr/js/structurizr-diagram.js` (`applyAutomaticLayout`, around line 6844) hands the whole JointJS graph to `joint.layout.DirectedGraph.layout` with `rankDir` mapped from `TopBottom|BottomTop|LeftRight|RightLeft` to `TB|BT|LR|RL`, `rankSep`, `nodeSep`, `edgeSep` passed through unchanged, `setLinkVertices` from the view's `vertices` flag, `marginX`/`marginY` 0, and `resizeClusters: true` with `clusterPadding` 50 on all four sides. The defaults when a view has no settings are in `structurizr-ui.js` lines 8–12: `LeftRight`, 100, 50, 50, `true`. The container view's software-system boundary, groups and deployment nodes are all JointJS *embedded* cells, and `DirectedGraph.toGraphLib` turns every embedding into a graphlib `setParent`, so Dagre already runs in compound mode today. After Dagre returns, JointJS calls `fitToChildren({ padding: 50, deep: true })` from the deepest boundary upwards, which replaces Dagre's own cluster rectangles with the children's bounding box plus padding. Edge points come straight from Dagre's dummy-node chain, simplified with a 0.001 collinearity threshold and stripped of their first and last point before they become vertices.

Two facts about this pipeline matter for the comparison. First, Dagre's own cluster boxes are *not* what users see: on the Live deployment view Dagre reports `bigbank-db01` as 1800×500 and `Oracle - Primary` as 1700×400, the fit pass shrinks them to 650×500 and 550×400 (measured by `layout-dagre.js`, which keeps both). Any new engine wrapper around Dagre has to keep that pass or boundaries come out bloated. Second, **Dagre throws on an edge whose source or target is a compound node** (`rank/util.js`: `Cannot set properties of undefined (setting 'rank')`). Big Bank's Live deployment view contains exactly such an edge, relationship 93 "Replicates data to" from deployment node `Oracle - Primary` to deployment node `Oracle - Secondary`. The vendored renderer passes every link into the layout, so with `automaticLayout` set on that view the exception is caught by the `try/catch` in `applyAutomaticLayout`, logged as "There was an error applying the automatic layout", and the view is left unlaid. Big Bank ships with stored coordinates so nobody sees it there, but any workspace with `autoLayout` and a deployment-node-to-deployment-node relationship hits it today.

## Method

Everything lives under [`docs/research/compound-layout/`](compound-layout/). `view-graph.js` converts one Structurizr view into a renderer-neutral compound graph (leaf boxes 450×300, Person 400×400, element-style overrides honoured; boundaries sized by the engine; empty deployment nodes dropped as the renderer does). `layout-dagre.js` reproduces the JointJS adapter call for call, including the fit pass and the polyline simplification, and adds a `clusterEdges` strategy for the crash described above. `layout-elk.js` builds the nested ELK JSON with each edge placed in the lowest common ancestor of its endpoints and flattens ELK's parent-relative coordinates back to absolute ones. `geometry.js` checks containment (every child inside its parent), sibling overlap, leaves covered by a foreign boundary, polyline crossings, and writes SVG previews. `bench.js` runs the lot; `bundle-size.js` measures bundles with esbuild; `layout-graphviz.js` is the third-option probe. Six previews are committed under [`previews/`](compound-layout/previews/). The Big Bank workspace itself is not committed; fetch it with `curl -sSL -o docs/research/compound-layout/big-bank-plc.json https://raw.githubusercontent.com/structurizr/ui/main/examples/big-bank-plc.json`, then `pnpm add -D elkjs esbuild @hpcc-js/wasm-graphviz` temporarily and run `node docs/research/compound-layout/bench.js --svg out`.

Big Bank has no groups, so the "Containers+groups" cases put the five containers into two synthetic groups ("Channels" and "Backend") inside the software-system boundary, which exercises boundary → group → element nesting at depth 2. The Live deployment view is depth 3 (`Big Bank plc` → `bigbank-api***` → `Apache Tomcat` → `API Application`), 7 leaf elements, 13 boundaries, 7 edges. All runs use the renderer's defaults (`LeftRight`, 100, 50, 50, vertices on) unless marked TB. Timings are Node 24 on an Apple Silicon laptop, median of 30 warm runs plus the first (cold) call in each process.

## 1. Nesting: children inside parents, parents sized to fit

Both engines pass. Across all six cases neither produced a child outside its parent, a pair of overlapping siblings, or a leaf covered by a boundary it does not belong to (the `escapes`, `sibling overlaps` and `foreign boundary` columns below are all zero). ELK sizes compound nodes natively from their children plus `elk.padding`. Dagre sizes clusters too, but inflates them to span every rank its nesting edges touch (the 1800×500 `bigbank-db01` above), which is why the fit pass is load-bearing; with it, the two engines produce boundaries of the same size for the same children.

Where they differ is *placement*, and this is the heart of the qualitative comparison (section 5). A layered algorithm has to make each compound node a contiguous block of layers. In the Live view `Web Application` (inside Big Bank plc) feeds the `Single-Page Application` (in the customer's computer, outside Big Bank plc), which feeds `API Application` (inside Big Bank plc again). Dagre resolves this by stretching `Big Bank plc` across ranks 0–3, the whole 4200 px width, and parking the customer's computer above and the mobile device below that giant, mostly empty box. ELK keeps `Big Bank plc` compact (the whole diagram is 3766×1280 instead of 4200×2651) by putting the customer's computer to the *right* of the bank and routing the SPA → API edge back across the diagram as one long reversed edge. Both are correct nestings; they are different pictures.

## 2. Mapping the five Structurizr settings

| Structurizr `automaticLayout` | Dagre (as the renderer passes it) | ELK (`elk.layered`) |
|---|---|---|
| `rankDirection` TopBottom / BottomTop / LeftRight / RightLeft | `rankdir` `TB` / `BT` / `LR` / `RL`; one-to-one | `elk.direction` `DOWN` / `UP` / `RIGHT` / `LEFT`; one-to-one |
| `rankSeparation` (px between ranks) | `ranksep`; one-to-one | `elk.layered.spacing.nodeNodeBetweenLayers`; one-to-one. ELK also has `edgeNodeBetweenLayers` and `edgeEdgeBetweenLayers` for the gaps edges keep from nodes between layers, which Dagre folds into `ranksep`; the probe sets the first to half the rank separation and the second to the edge separation |
| `nodeSeparation` (px between nodes in a rank) | `nodesep`; one-to-one | `elk.spacing.nodeNode`; one-to-one, plus `elk.spacing.componentComponent` for disconnected components, which Dagre has no knob for |
| `edgeSeparation` (px between parallel edges) | `edgesep`; one-to-one | `elk.spacing.edgeEdge` and `elk.spacing.edgeNode`; there is no single ELK option, two have to be set |
| `vertices` (emit bend points) | Dagre always returns `points`; JointJS keeps them as vertices when the flag is on and discards them otherwise | ELK always returns `sections[].bendPoints`; keep or discard the same way. `elk.edgeRouting` picks the shape: `POLYLINE` is closest to Dagre's output, `ORTHOGONAL` is what most React Flow users expect, `SPLINES` also exists |
| boundary padding (50 px, not a view setting) | `clusterPadding` on the JointJS fit pass; Dagre itself has none | `elk.padding: [top=50,left=50,bottom=50,right=50]` on every compound node |

Dagre's mapping is the renderer's mapping, so a Dagre-based engine reproduces today's spacing by construction. ELK's is a close but not exact translation: two of the five settings fan out into more than one ELK option, and ELK has further defaults (`spacing.portPort`, `layered.spacing.baseValue`) that silently participate. Neither engine has anything to add for `BottomTop`/`RightLeft` beyond the direction constant.

## 3. Bundle size

Measured with esbuild (`bundle`, `minify`, ESM, browser platform), gzip at default level, by `bundle-size.js`:

| Entry | Minified | gzip | brotli |
|---|---:|---:|---:|
| `@dagrejs/dagre` 1.1.8 (pulls in `@dagrejs/graphlib`) | 41.3 kB | 14.4 kB | 13.1 kB |
| `elkjs/lib/elk.bundled.js` (API + engine in one chunk, no worker) | 1426.0 kB | 432.4 kB | 330.6 kB |
| `elkjs/lib/elk-api.js` (main-thread API only, needs a worker) | 5.2 kB | 2.1 kB | 1.9 kB |
| `elkjs/lib/elk-worker.min.js` (the worker, shipped pre-minified) | 1418.0 kB | 429.3 kB | 328.1 kB |
| `elkjs/lib/elk-worker.js` (unminified worker, re-minified by esbuild) | 1890.1 kB | 460.8 kB | 356.9 kB |
| For scale: Renderizr's whole JS today (`node scripts/build.js architecture/workspace.json`, all chunks) | 996 kB | 303 kB | — |

ELK is roughly thirty times Dagre and 1.4× the entire current application, gzipped. The engine is GWT-compiled Java (`elk-worker.min.js`), which is why it does not tree-shake; `algorithms` passed to the `ELK` constructor only controls which algorithms are *registered*, not which are *bundled*. ELK does not strictly need a web worker: `elk.bundled.js` runs the engine on the calling thread through a fake worker object, and at these graph sizes a 10–15 ms synchronous call is harmless. The worker variant is the same bytes split across two files (2.1 kB + 429 kB), so it buys responsiveness on large graphs, not bytes. It also complicates `--single-file`: the `renderizr:single-file` plugin in `scripts/plugins.js` inlines every chunk into one HTML document, so a worker would have to be spawned from a `Blob` URL built from an inlined string, and Vite's `new Worker(new URL(...))` output would need special handling there. Both licensing and provenance differ too: Dagre is MIT; elkjs is `EPL-2.0 OR GPL-3.0-or-later`, a weak copyleft that would need its own entry and source-availability statement in `THIRD-PARTY-NOTICES.md` and `NOTICE`, the same shape of obligation the project already discharges for JointJS under MPL-2.0 but a license the project has not yet taken on.

Both are fast enough that layout time is not a deciding factor: the slowest case is Dagre at 27 ms warm on the Live view, and ELK's one real cost is the first call in a process (110–140 ms, JIT warm-up of 1.4 MB of generated code), which a page pays once. Dagre's compound mode is slower than ELK warm because its nesting graph multiplies every edge's `minlen` by a factor proportional to the nesting depth (`lib/nesting-graph.js`) and the network-simplex ranker then works on that expanded graph; the 20-element Live view is still under 30 ms. The "elk separate" rows are `hierarchyHandling: SEPARATE_CHILDREN`, ELK's default, included to show it is **not** an option for Structurizr: it lays out each boundary in isolation and routed 0 of the 7 edges on the Live view, because every relationship there crosses a boundary. `INCLUDE_CHILDREN` is mandatory.

## 5. How far each lands from the current renderer

Dagre lands where the renderer lands today, because it *is* the renderer's algorithm with the renderer's parameters; `layout-dagre.js` reproduces the JointJS adapter call for call (same graph label, same per-edge `minlen`/`weight`, same fit pass, same simplification), so it yields the same ranks, the same order within ranks and the same polylines, with one input the probe leaves at zero that the renderer fills in: the label width/height JointJS attaches to each edge, which nudges spacing on labelled relationships. The only other divergence is deliberate: the renderer would have thrown on the Live view's deployment-node edge and shown nothing, whereas the probe's `redirect` strategy attaches that edge to an invisible 1×1 anchor node inside each boundary so the layout completes. The preview [`livedeployment-lr--dagre.svg`](compound-layout/previews/livedeployment-lr--dagre.svg) shows the cost of that trick: the edge is drawn to the anchor's position inside the boundary, so a real implementation has to re-clip it to the boundary's border afterwards. The familiar Dagre look is also visible there: diagonal polyline segments between ranks, and the `Big Bank plc` boundary stretched across every rank its children occupy, leaving large empty areas inside it.

ELK with `INCLUDE_CHILDREN` lands somewhere recognisably different. Its diagrams are 45–70% smaller in bounding-box area across the six cases, boundaries hug their contents, edges are nearly orthogonal even in `POLYLINE` mode and fully so in `ORTHOGONAL`, and it handles the boundary-to-boundary edge natively (routed to the `Oracle` boundaries' borders with no anchor trick, see [`livedeployment-lr--elk-include.svg`](compound-layout/previews/livedeployment-lr--elk-include.svg)). The price is that it makes different placement decisions. On the Live view it moves the customer's computer to the far side of the bank and runs one long edge back; a Structurizr user who has seen the same view in Structurizr Lite (Graphviz) or on-premises (this Dagre path) would notice the change immediately, and the autolayout knobs they tuned (`rankSeparation 300` to spread a Graphviz layout, as `architecture/workspace.json` does) would mean slightly different things. For a view with groups ([`containers-groups-lr--dagre.svg`](compound-layout/previews/containers-groups-lr--dagre.svg) versus [`containers-groups-lr--elk-include.svg`](compound-layout/previews/containers-groups-lr--elk-include.svg)) both produce the expected boundary → group → element nesting with the external systems outside; ELK's is tighter and its edges leave the boundary as short near-orthogonal runs, Dagre's cross it diagonally.

In short, Dagre is "the same as today, including today's quirks", ELK is "better-looking, different, and 30× the bytes".

## Third options, one sentence each

**Graphviz `dot` via WebAssembly (`@hpcc-js/wasm-graphviz` 1.29.2, Apache-2.0)** is the engine behind Structurizr's own `autoLayout` (the `"implementation": "Graphviz"` in `architecture/workspace.json`), supports clusters and cluster-anchored edges (`compound=true`, `lhead`/`ltail`), and was the fastest thing measured (Live view 1.9 ms median, Containers 1.4 ms, 41 ms to instantiate), but the wasm is inlined as base64 and the bundle is 617 kB gzipped, bigger than ELK; it is the right answer only if matching Structurizr CLI output pixel-for-pixel becomes a goal.

**ELK `SEPARATE_CHILDREN`, or Dagre run recursively per boundary with each laid-out boundary treated as a fixed-size node in its parent** (the "manual compound pre-pass"), both collapse cross-boundary edges to the boundary border and lose the ability to rank an inner element against an outer one; since nearly every Structurizr relationship crosses a boundary (7 of 7 on the Live view), the result is the "0 edges routed" row above and it is not a contender.

**d3-hierarchy** (`pack`, `treemap`, `tree`) lays out containment only and knows nothing about edges, so it could place nested deployment nodes attractively for a view with no relationships but has no answer for ranks, flow direction or the five settings; not a contender for autolayout, though `treemap`-style packing could be a fallback for boundaries whose children have no edges.

**WebCola** (constraint-based force layout with group support, ~100 kB) honours nesting through group constraints but is iterative, order-dependent and non-layered, so it cannot express rank direction or rank separation at all and converges in hundreds of milliseconds rather than tens; it is the furthest from the Structurizr look and not a contender.

## Recommendation

Keep `@dagrejs/dagre` and make the new engine's layout step a faithful port of what `@joint/layout-directed-graph` does today, without JointJS: build a compound graphlib graph with `setParent` for every boundary, group and deployment node; pass the five settings through one-to-one as the table in section 2 shows; run the fit-to-children pass with 50 px padding from the deepest boundary up (Dagre's own cluster boxes are not usable); simplify the returned points with the 0.001 threshold and drop the end points before using them as vertices. That reproduces today's output for every view that works today, costs 14 kB gzipped that is already in the bundle, stays MIT, needs no worker and no `--single-file` changes, and keeps `architecture/workspace.json`'s and users' tuned `rankSeparation`/`nodeSeparation` values meaning what they meant.

Add two guards the current renderer lacks. First, before layout, redirect any edge whose endpoint is a compound node to a zero-size anchor node parented inside it (the `redirect` strategy in `layout-dagre.js`), then after layout clip that edge's first or last segment to the boundary rectangle; without this, a workspace with a deployment-node relationship and `autoLayout` renders nothing, as it does in the vendored renderer today. Second, treat an `automaticLayout` whose `applied` is `true` as "coordinates are present": `architecture/workspace.json` has `"applied": true, "implementation": "Graphviz"` *and* stored x/y from the Structurizr CLI, yet the vendored renderer re-runs Dagre whenever `view.automaticLayout` is set at all (`structurizr-diagram.js` line 988), discarding the Graphviz result; the new engine should only lay out when coordinates are actually missing, and otherwise use what is stored. Whether to lay out on the main thread is not a question for Dagre at these sizes (sub-30 ms).

Revisit ELK only if a concrete requirement appears that Dagre cannot meet: orthogonal edge routing as a product feature, views in the hundreds of elements where Dagre's compound ranking becomes slow, or a decision that Renderizr should look better than Structurizr rather than the same. If that day comes, use `elk.bundled.js` on the main thread (no worker, no single-file surgery), `INCLUDE_CHILDREN`, `POLYLINE` routing for the closest match to today, the option mapping in section 2, and add the EPL-2.0 entry to the third-party notices. The engine contract ([#27](https://github.com/FormulaMonks/renderizr/issues/27)) should therefore take a layout *function* of the shape `(compoundGraph, settings) → { boxes, edges }` as in these probes, so swapping the implementation later is a one-file change.

## Notes for later tickets

For the boundaries ticket ([#30](https://github.com/FormulaMonks/renderizr/issues/30)): React Flow sub-flows take positions *relative to the parent node* (`parentId` + `extent: "parent"`), Dagre returns absolute centre coordinates, so the conversion is centre → top-left → subtract the parent's top-left, and the parent's own size has to be written from the fit pass before its children are positioned; ELK would hand back parent-relative coordinates natively, which is one of its genuine conveniences. Empty deployment nodes should be removed before layout, as the renderer does, or they become 0×0 compound nodes. Groups are boundaries for layout purposes (`findOrCreateGroup` embeds exactly like a boundary), including nested groups when `structurizr.groupSeparator` is set.

For the engine contract ([#27](https://github.com/FormulaMonks/renderizr/issues/27)): the five settings plus the 50 px padding are the whole input; the output is absolute boxes for every node including boundaries, and per-edge polylines whose interior points are the vertices when `vertices` is true. Edges whose endpoint is a boundary must be representable, since the model allows them. The Big Bank Live view is a good fixture precisely because it has one.
