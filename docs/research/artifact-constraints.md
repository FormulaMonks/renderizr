# Artifact and single-file constraints on a React bundle

Research for [issue #26](https://github.com/FormulaMonks/renderizr/issues/26), part of the React Flow engine effort mapped in [#21](https://github.com/FormulaMonks/renderizr/issues/21). The question: does a React + `@xyflow/react` bundle survive the `--single-file` build and the Claude artifact host unchanged, and what does the island need from the page around it?

## Summary

Nothing in the single-file or artifact pipeline blocks the React Flow island. The production bundle passes `makeArtifactSafe` byte for byte unchanged with zero `findUnspellable` hits; the CSP it needs is exactly the CSP the current output already needs (`script-src 'unsafe-inline'` for the inlined module script, `style-src 'unsafe-inline'` for the inlined stylesheet), and React's own inline styles turn out not to be subject to CSP at all; the library makes no network request, loads no font and starts no worker; and a root per page visit, unmounted before the container is wiped, is the lifecycle that fits the existing `Page.render()`/`clear()` contract. The one thing that does need handling is the 0x0 container: React Flow recovers its own dimensions when the box gains size, but `fitView` is a one-shot queue that it consumes against whatever size it had at the moment the nodes were measured, so the island must either be mounted only once the container is measurable (what `whenMeasurable` already does) or call `fitView()` again when the container's size changes. The island costs 407 kB minified / 129 kB gzipped, of which React itself is 222 kB / 69 kB.

## Method

A tiny Vite 7.3.6 app (`react@19.3.0`, `react-dom@19.3.0`, `@xyflow/react@12.12.0` on `@xyflow/system@0.0.83`) renders a two-node, one-edge flow with `fitView`, `<Background>` and `<Controls>` into `#structurizr-diagram-target`, built with the same output options as `scripts/config.js` (`target: "esnext"`, `cssCodeSplit: false`, `modulePreload: false`, `manualChunks: undefined`, `inlineDynamicImports: true`). Its minified chunk was run through the repository's own `makeArtifactSafe` and `findUnspellable` from `scripts/escapes.js`, then assembled into single-file pages the way `singleFile()` in `scripts/plugins.js` assembles them: the stylesheet in a `<style>`, the escaped code in a `<script type="module">`. Each page was opened in Google Chrome (the headless `--dump-dom` path the e2e suite uses, and then Playwright driving the installed Chrome in real time, because `--virtual-time-budget` advances timers without rendering frames and `ResizeObserver` callbacks only run at a rendering opportunity, which made the resize scenarios inconclusive under `--dump-dom`). The page wrote everything observable into the DOM: store size, container size, `useNodesInitialized`, the viewport transform, every `onError` code, every `securitypolicyviolation` event and every `window.error`. The harness is under [`artifact-constraints/`](./artifact-constraints/) next to this document.

## 1. Does the bundle survive `makeArtifactSafe` unchanged?

Yes, literally unchanged. `findUnspellable` finds nothing in the 406,833-byte minified chunk or the 15,869-byte stylesheet, and `makeArtifactSafe` returns the input string itself (`safe === js`), adding zero `String.fromCharCode` terms and zero `RegExp(` rewrites. React, `react-dom`, `scheduler`, `@xyflow/react`, `@xyflow/system`, `zustand`, `classcat`, `d3-selection`, `d3-zoom` and `d3-drag` contain no U+FFFD literal and no `\uD800`-style surrogate escape; the two things the escapes module exists for come from `mdurl`, `markdown-it`, `uc.micro` and jQuery, none of which the island touches. The chunk also contains no `__VITE_PRELOAD__` marker, since nothing in the island is dynamically imported.

The escaped code executes: the six test pages render two `.react-flow__node` elements with `translate()` transforms, one `.react-flow__edge-path`, and a fitted viewport (`translate(29px, 86.51px) scale(1.455)` for a 640x400 box) with no page error. The `makeArtifactSafe` parse itself is an extra guarantee: `parseAst` reads the whole 407 kB module as an ES module, so a chunk that passes it is at least syntactically what Rollup emitted.

Two things the pipeline does today still apply and need no change. The chunk is inlined as `<script type="module">`, which is what the `SCRIPT_TAG` replacement produces; React Flow's stylesheet (`@xyflow/react/dist/style.css`, imported once from the island module) is emitted as the single CSS asset `cssCodeSplit: false` produces and lands in the `<style>` block `STYLE_TAG` produces. In `artifact.html` the styles come first, then the markup, then the module scripts, which is the order the island needs (its stylesheet is present before the first measurement).

## 2. CSP: what the island needs and what the artifact host enforces

What React Flow does at runtime: it positions nodes and the viewport with `style` props (`transform: translate(...)`, see `@xyflow/react/dist/esm/index.js:2361` for nodes and the viewport's `transform` derived from the store), draws edges and the background pattern as SVG with attributes and `url(#id)` fragment references, and injects nothing with `<style>`, `insertRule` or `adoptedStyleSheets` (grep of both `@xyflow` packages: zero hits). Its stylesheet is the `style.css` the application imports; the library adds no CSS at runtime.

How React applies a `style` prop matters for CSP: `react-dom` writes `node.style[name] = value` and `node.style.setProperty(...)` (`react-dom-client.production.js`, `setValueForStyle`/`setValueForStyles`), that is, through the CSSOM, never through a `style="..."` attribute string. CSP's `style-src` (and `style-src-attr`) governs `<style>` elements, `<link>`ed sheets, `style` attributes in markup and `setAttribute("style", ...)`; it does not govern CSSOM property writes. The test page with `style-src 'sha256-PLACEHOLDER'` (no `'unsafe-inline'`) proves it: Chrome logged exactly two violations, one for each inlined `<style>` element, while all twelve React-set `style` attributes applied and the nodes and viewport were transformed correctly. So the island's only CSP need on the style side is whatever the inlined stylesheet needs, and that is a need the current output already has for its own CSS.

The directives the island needs, in full: `script-src 'unsafe-inline'` (the inlined module script, same as today; no `eval`, no `new Function`, no `'unsafe-eval'` needed, and `'unsafe-eval'` is irrelevant because the inline module is a script element, not a string evaluation), `style-src 'unsafe-inline'` (the inlined stylesheet, same as today), `img-src data:` only if a workspace embeds raster images (same as today; React Flow itself draws no images), and nothing else: no `connect-src`, `font-src`, `worker-src`, `frame-src` or `child-src` is exercised. With the artifact-style policy `default-src 'none'; script-src 'unsafe-eval' 'unsafe-inline'; connect-src 'none'; worker-src blob:; style-src 'unsafe-inline'; img-src blob: data:; font-src data:; object-src 'none'; base-uri 'none'; form-action 'none'` as a `<meta>` tag, the page behaved identically to the page with no CSP: no violation, same render.

What the Claude artifact host enforces. The CSP header captured from a claude.ai artifact by [Simon Willison in October 2024](https://simonwillison.net/2024/Oct/21/claude-artifacts/) reads `default-src https://www.claudeusercontent.com; script-src 'unsafe-eval' 'unsafe-inline' https://www.claudeusercontent.com https://cdnjs.cloudflare.com https://cdn.jsdelivr.net/pyodide/; connect-src https://cdn.jsdelivr.net/pyodide/; worker-src https://www.claudeusercontent.com blob:; style-src 'unsafe-inline' https://www.claudeusercontent.com https://cdnjs.cloudflare.com https://fonts.googleapis.com; img-src blob: data: https://www.claudeusercontent.com; font-src data: https://www.claudeusercontent.com; object-src 'none'; base-uri https://www.claudeusercontent.com; form-action https://www.claudeusercontent.com; frame-ancestors ...; upgrade-insecure-requests; block-all-mixed-content`. Both `'unsafe-inline'` keywords are present. For the Claude Code artifact host (`claude.ai/code/artifact`, served from a sandboxed `*.claudeusercontent.com` origin), the [official documentation](https://code.claude.com/docs/en/artifacts) does not print the header but describes it: "a strict Content Security Policy" under which scripts may load from five CDN hosts and typefaces from Google Fonts, "every external image and all other external scripts, stylesheets, and fonts" are blocked, and Claude "inlines all other CSS and JavaScript", which only works if inline `<style>` and inline `<script>` are permitted, i.e. `'unsafe-inline'` on both. The Artifact tool's own instructions to Claude say the same ("puts everything else inline"), and the existing `artifact.html` output, whose `<style>` block and inline module script already depend on both keywords, renders on that host today (that is what the `--single-file` artifact path exists for). A `style-src` without `'unsafe-inline'` would break the current output before it broke the island.

Residual risk and how to verify it: the directive to watch is `style-src`, and only for the `<style>` element; a host that moved to nonces or hashes for styles would break the current stylesheet and the island's alike, and nothing else in the island depends on policy. A one-page probe artifact that checks each mechanism (inline `style` attribute in markup, CSSOM write, `setAttribute("style")`, `<style>` element, inline script, a `blob:` worker, `fetch` of its own URL and of an external one) and lists every `securitypolicyviolation` event it received is published privately at https://claude.ai/artifact/LkcqaEd8rPfFJX8oyytt8k; its source is [`artifact-constraints/csp-probe.html`](./artifact-constraints/csp-probe.html). This research session could not sign in to read it back (the browser pane it had was unauthenticated and signing in is outside what it may do), so it was not read here; opening it while signed in gives the answer for the live host in one glance, and republishing the same file to the host answers it again after any host change.

## 3. The 0x0 container

What React Flow does at mount, from `@xyflow/react@12.12.0` `dist/esm/index.js`. `useResizeHandler` (lines 1265 to 1290) measures the pane with `offsetWidth`/`offsetHeight` once at mount, on every `window` `resize`, and from a `ResizeObserver` on the pane element. If the element fails `checkVisibility()` (for example `display: none`) it returns without writing anything. If it is visible but either dimension is 0 it calls `onError('004', 'The parent container needs a width and a height to render the graph.')` and then writes `width: size.width || 500, height: size.height || 500` into the store: a 0x0 box becomes a fictitious 500x500 one. `fitView` as a prop sets `fitViewQueued: true` in the initial state (line 3345), and the queue is consumed in exactly two places: `setNodes` when `fitViewQueued && nodesInitialized` (line 3446) and `updateNodeInternals` when `fitViewQueued` (line 3489), both of which call `resolveFitView()`, which fits against the store's `width`/`height` at that instant and then clears the queue. Nothing re-queues it on resize; the store's `width`/`height` are updated by the `ResizeObserver` and are used by the next explicit `fitView()`, zoom or pan, but no fit happens on its own. (Nodes are measured by a separate per-node `ResizeObserver`, `useResizeObserver` at line 2147, which is what flips `useNodesInitialized`.)

Measured, in a 0x0 `#structurizr-diagram-target` that is given 640x400 after 1.2 s: error 004 fires at mount (twice, once from the initial call and once from the observer's initial notification), the store reads 500x500, the nodes are measured at 150x36 anyway (an `overflow: hidden` 0x0 box still lays out absolutely positioned children), `fitView` resolves at about 170 ms against 500x500 to `translate(22px, 161.08px) scale(1.14)`, and when the box gains size the store updates to 640x400 within a frame but the viewport stays at `scale(1.14)`; the correct fit for that box is `scale(1.455)`. In a `display: none` container shown after 1.2 s the picture is worse: `checkVisibility()` is false so the store stays 0x0, the nodes measure 0x0 so they are not initialized and the queue stays armed, and when the box is shown the nodes' observers fire first, `updateNodeInternals` resolves the queued fit against the still 0x0 store, `getViewportForBounds` clamps to `minZoom`, and the result is `translate(-100px, -39px) scale(0.5)` with the nodes half off the pane; the pane's own observer then updates the size to 640x400 without re-fitting.

So: React Flow's own `ResizeObserver` recovers its dimensions but not its fit, and `fitView` must be re-run once the container has a real box. Two ways to do that, and the recommendation is to do both. Keep `whenMeasurable` gating the mount, exactly as `src/pages/diagrams.ts` does today, so the island never sees the 0x0 or hidden state at all (this also avoids the console noise of error 004 and the one wasted fit); and wire the width observer the page already keeps (`#resizeObserver` in `diagrams.ts`, which drives `#fitDiagram` on width change) to the engine's fit operation, which in React Flow is `useReactFlow().fitView()` (an async method that returns `Promise<boolean>` and reuses one resolver if called repeatedly, line 1218). Alternatively, suppress code 004 in `onError` as the [xyflow discussion #2927](https://github.com/xyflow/xyflow/discussions/2927) suggests and fit from the observer only; this works but relies on the fake 500x500 fallback and is uglier than not mounting early. The canvas-height logic in `#fitDiagram` (size the box from the diagram's own aspect ratio, then fit) maps onto the engine as `getNodesBounds(nodes)` for the aspect ratio followed by `fitView()`; the exported `getViewportForBounds(bounds, width, height, minZoom, maxZoom, padding)` is the same function React Flow fits with, usable to predict the zoom before committing a height.

## 4. `file://` and offline

Confirmed: the island makes no runtime request. Over HTTP, Playwright recorded one request per page (the HTML document itself; Chrome's own `favicon.ico` probe produced the only 404). The headless `--dump-dom` runs opened the same pages from `file://`, where a `<script type="module">` inline in the document is permitted (it is the external module `src` that `file:` refuses, which is why the single-file build inlines), and rendered the nodes and edge. A grep of both `@xyflow` ESM bundles and both stylesheets finds no `fetch(`, `XMLHttpRequest`, `new Worker`, `importScripts`, `import(`, `@font-face`, `@import` or `url(` to anything but SVG fragment ids (`url('#marker-id')`, `url(#pattern-id)`). `style.css` sets no `font-family` at all; the island inherits the page's font, which is already embedded by `branding()` when `--font` is given. `window.matchMedia`, `ResizeObserver` and `requestAnimationFrame` are the only platform APIs it leans on, all synchronous and local. The `no-network.js` fixture that poisons `fetch` in the e2e builds would not notice the island, and the "renders with no server, no siblings and no network" test in `test/e2e.test.js` would keep its meaning with `.react-flow__node` standing in for `svg`.

## 5. Mount lifecycle with the hash router

How the page is torn down today: `Router.navigateTo` calls `currentPage.clear()`, which for `Diagrams` ends with `this.container.innerHTML = ""`, and then `render()`, which writes a fresh template containing a new `#structurizr-diagram-target`. The island's container element therefore does not survive a page change; a persistent root would need a container that is kept out of that `innerHTML` and re-appended on each visit, which is a restructuring of `Page` for no gain, because a workspace is static data and re-creating the flow is cheap (the second and third mounts in the remount test initialized 6 and 11 ms after `createRoot`). One root per page visit is simpler and fits the existing contract: `render()` writes the template, waits for `whenMeasurable`, then `createRoot(target).render(<Island/>)`; `clear()` calls `root.unmount()` before `innerHTML = ""` and drops the reference.

Why unmount before wiping, with the React docs as the source: `root.unmount` "will unmount all the components in the root and 'detach' React from the root DOM node, including removing any event handlers or state in the tree", and it is needed precisely when "your React root's DOM node (or any of its ancestors) may get removed from the DOM by some other code", because otherwise "the components inside the removed root won't know to clean up and free up global resources like subscriptions" ([createRoot reference](https://react.dev/reference/react-dom/client/createRoot)). Measured: wiping `innerHTML` and creating a new root on the same element throws nothing in the production build and renders correctly, so the leak is silent; what leaks per visit is the previous root's fiber tree, its zustand store, its `window` `resize` listener from `useResizeHandler` (whose cleanup only runs on unmount) and its node `ResizeObserver`s. After `root.unmount()` the container has zero children, and `createRoot` on the same element again is explicitly supported ("you can create a new root for the same DOM node after the previous root for that node has been unmounted"); what is not allowed is `root.render` on an unmounted root, which throws "Cannot update an unmounted root", so the page must create a new root each visit rather than reuse the old handle. React 19 attaches its event delegation to the root container, not `document`, so unmounting also removes the delegated listeners. The one observer React Flow deliberately never disconnects, `XYPanZoom`'s pane extent `ResizeObserver` (`@xyflow/system` lines 2967 to 2988), observes only the pane element and is garbage collected with it.

StrictMode: all its checks are "development-only and do not impact the production build" ([StrictMode reference](https://react.dev/reference/react/StrictMode)), so the shipped artifact is unaffected whether or not the island is wrapped in it. In `vite` dev it double-invokes effects (mount, cleanup, mount), which React Flow 12 tolerates; the test pages were wrapped in `<StrictMode>` and the production runs show every effect once. The one thing to avoid in page code is doing work in a `useEffect` that is not idempotent across that double invocation, for example registering the `wheel`/`pointer` handlers `diagrams.ts` currently adds imperatively; moving them into the island as React props or into an effect with a cleanup is enough.

What the router needs from the island: nothing it does not already have. The hash router (`history/hash`) owns the URL and the `?page=` parameter and calls `render()`/`clear()`; the island needs no knowledge of it. If view changes should be deep-linkable later, the island can read a `view` parameter in `render()` and the page can call `history.replace` when the engine reports a view change, the way `#diagram.onViewChanged` is used today, with no React Router involved.

## Bundle size

From the tiny build with Vite 7.3.6 and the repository's output options: the island chunk is 406,833 bytes minified and 129,325 bytes gzipped (level 9), plus 15,869 bytes of stylesheet (2,658 gzipped), so 407 kB / 132 kB gzipped added to the single-file output in total. React and `react-dom` alone, rendering one element, are 221,890 bytes / 69,054 gzipped of that; `@xyflow/react`, `@xyflow/system`, `zustand`, `classcat` and the three d3 modules are the remaining 185 kB / 60 kB.

For scale, the fixture workspace's `artifact.html` today is 1,022,044 bytes / 319,326 gzipped. Of that, the parts the React Flow engine would replace are the vendored Structurizr renderer (173,812 minified / 36,283 gzipped as the `virtual:structurizr-renderer` string), `@joint/core` (440,355 / 133,244 as its own minified dist), `@joint/layout-directed-graph` (3,891 / 1,777), `@dagrejs/dagre` (97,199 / 29,318) and jQuery (87,533 / 30,342), together roughly 800 kB / 230 kB. Dagre would come back if the engine keeps it for automatic layout. Net, replacing the engine shrinks the artifact rather than growing it; adding the island beside the current engine (a transition period) grows it by about 40%, to about 1.4 MB / 450 kB gzipped, still well under the host's 16 MiB cap.

## What the engine contract (#27) should take from this

The engine should expose a `fit()` operation (mapping to `fitView()`) that the page calls from its width observer, because the library will not refit on its own. The engine should be mounted only once the container is measurable, so `whenMeasurable` moves to the island boundary rather than disappearing. The engine's lifecycle is `mount(container) -> unmount()` with a fresh root per mount and `unmount()` guaranteed before the DOM is removed. Nothing the engine does may rely on a `style` attribute written as a string (keep to React `style` props and class names) or on a runtime `<style>` injection, so the CSP story stays identical to today's. Dagre is already a dependency and runs in the main thread; layout can stay synchronous and local.
